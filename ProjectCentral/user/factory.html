#0 · Why?

Keep the reason for making software alive

Agentic development can produce working changes while losing the purpose and experience that made them worth asking for. Factory exists to carry human intention through development and returned reality, freeing the person from repeated orientation and mechanical supervision while preserving consequential judgment.

README.md
#1 · What?

A durable software development system

Software Factory is a native development system with a Rust semantic core, a factory command surface and a Build presentation. It relates Projects, continuing Journeys, bounded Runs, Claims, Evidence, Decisions and Candidates so an intended transformation remains inspectable across sessions, tools and material environments.

README.md
#2 · How?

Commission, develop, encounter and return

Start from the Project’s recognised purpose and a concrete intended difference. Recover the required source and conditions, carry out bounded development, make the resulting Candidate and Evidence encounterable, and return through Recognition or revision. Keep the exact intent, context, execution and evidence relations throughout.

README.md
#3 · Who / Whereby?

People author; situated Agents carry development

The person or authorised governing locus determines consequential direction and recognises outcomes. Agents and AgentSets carry Journeys through bounded Runs. Factory supplies developmental continuity; Actuation supplies authority, AIKit the operative context and body, Workcell material execution, and Central durable source ground.

README.md
#4 · Where / When?

Across Projects, sessions and changing Worlds

Factory operates where software development needs continuity beyond a terminal or conversation. A Journey can span Runs and absences; a Run keeps its identity across execution changes. Native CLI, Build and external projections read the same developmental subjects. Ordinary projects remain valid without a special ontology or QL runtime.

README.md
#5 · Why-For?

More room for authorship, better returned understanding

Success means a person can commission meaningful work, leave routine development to capable collaborators, and return to a clear result or consequential decision. The Project retains why its reality changed and what it learned. Evidence can improve implementation, methods or intention through the owner responsible for each.

vision

Software that preserves what was worth making

A request often names a feature because the person wants a different experience. An Agent can satisfy the vocabulary of that request while missing the experience. Factory starts from this gap: development should stay answerable to why the work exists as it becomes design, code and a result somebody can encounter.

The intended human experience is to commission a useful change and step away from routine mechanics. Source discovery, environment selection, decomposition, implementation and verification should not repeatedly demand the person’s attention. The person remains available where taste, purpose or a choice between materially different futures matters.

This is a product ambition, not a claim that the current checkout supplies every part of that experience. The account develops [[factory:seed:q0|the Why seed]] from the native README and original experienced ontology. Those sources establish the destination; native code and evidence establish which portions have become executable.

design-commitment

Make human attention consequential

Commission should recover what the Project and initiating request already determine. If the destination is clear, the Agent proceeds with authorised engineering work. If several possible outcomes change the Project’s purpose or intended experience, the system presents that difference for human determination. It does not ask the person to repeat existing ground.

At the other aperture, Recognition concerns the realised difference. A person should encounter a Candidate, understand its consequential claims and inspect evidence that supports or challenges them. Recognition may accept it, return it, select another possibility, revise the design or revise the original intention.

The design therefore gives attention a reason and a subject. A HumanRequest records a semantic Decision need across channels. Its presentation should explain what must be decided, why the Agent cannot derive that decision from existing authority, and how the available evidence bears on the alternatives.

For a new piece of work, the Agent first locates the Project’s purpose, relevant design commitments, present frontier and source revisions. It reads the smallest sufficient set, retaining addresses to the larger field. Existing knowledge may disclose these sources, but generated interpretation remains distinguishable from the source it interprets.

When the target already has an authored relational structure, development must preserve its identities and constitutive relations. The Agent identifies the exact root of the requested change, current bindings, absent positions and the acceptance needed to prove fidelity.

The same practice remains proportionate for an ordinary project. It need not invent coordinates, special headers or a ProjectCentral instance. Structural fidelity is a conditional obligation to an existing source, not a demand that every repository acquire another framework. A development system with a native command surface

At its most concrete, Factory provides a Rust-owned developmental model, a maintained factory executable and bounded versioned readings over native state. The command surface can list Journeys for a Project, inspect one Journey or Run with canonical identity and revision, expose the RunMap, Thought availability and execution/evidence correlations, and invoke a currently applicable Action through the canonical provider. Structured output lets another Surface consume the same owner state.

This gives a developer or Agent a practical entry: identify the Factory developmental provider and a canonical Project, Journey or Run reference, then request only the reading needed. An invocation preserves caller lineage and returns the native revision-changing receipt. Reopening the provider supplies the changed canonical state rather than a UI-local copy.

The current command surface remains narrower than the complete product vision. It now publishes the existing Journey/Run slice, while WorkflowUnit publication, heterogeneous Agency correlation, telemetry and AIKit consumption remain subsequent owner work. [[cap.factory.native-cli|Native CLI]] and [[cap.factory.build-reading|Build reading]] describe the implemented trace without claiming those later relations.

architecture-contract

Project, Journey and Run hold different durations

A Project is the enduring whole in which development has meaning. A Journey holds a continuing intended difference that can require several bounded transformations. A Run holds one such transformation. The Journey can retain participants, its frontier, related activity and returned results while no AgentSession is alive.

For example, a continuing effort to improve an application may need an exploratory Run, a Run that implements a chosen experience and a later correction. Their evidence remains attributable to those Runs. Journey continuity allows a collaborator to recover the purpose connecting them without treating all activity as one indefinitely growing execution.

One Run has one canonical RunMap derived from its identity. The map makes developmental relations inspectable; a host, projection or session replacement does not mint another Run. The document’s six composition layers are separate from the Run’s Ground → Intent → Design → Development → Application → Recursion traversal. [[cap.factory.journey-continuity|Journey continuity]] and [[cap.factory.run-map|Run topology]] retain these distinctions.

architecture-contract

An encounterable result with an inspectable reason

A Claim makes an assertion or interpretation addressable. Evidence bears upon it: it may support, challenge or qualify the claim. A Candidate gathers an experienceable possible result for comparison and Recognition. A Decision records a determination with its relevant authority and consequences.

These distinctions let a person ask why a proposed change belongs to the Project. The answer can lead from the Candidate to its claims, from those claims to evidence, and from evidence to the execution or source that produced it. Passing tests, merge state and the producing model’s confidence each carry information; none alone answers the question of Recognition.

When several Candidates reveal a useful synthesis, the synthesis becomes another or revised Candidate with ordinary evidence and decision treatment. It should not bypass review because its ingredients were previously considered. [[cap.factory.build-evidence|Candidate and evidence reading]] is the inspected presentation capability; complete experiential acceptance remains wider than that read model.

protocol-method

Commission an outcome and leave routine work to Agents

The person opens the Project and states the intended difference. The Agent recovers existing ground and explains the destination it understands, including any uncertainty that would materially change the result. Where the direction is already determined, the work proceeds. A genuine authorial ambiguity returns as a concrete choice with its evidence.

For continuing work, the Journey records the commission, accountable participant and closure conditions. A named Agent or AgentSet can carry the responsibility across bounded Runs. Each execution still receives its actual available Agency, context and material conditions through the native owners; membership of a Journey supplies no invocation authority.

While the person is absent, the Agent advances the relevant frontier and retains findings. When it needs Recognition, the visible request is attached to the developmental subject and explains the difference requiring attention. The intended result is continuity without constant supervision. [[cap.factory.journey-commission|Commission and handoff]] records the native developmental relation.

Compose the suite through native responsibilities

Factory owns Project development: Journeys, bounded Runs, their maps and developmental evidence, Candidate relations and Recognition consequences. Central owns the durable source side. AIKit resolves the operative context, knowledge and praxis; Actuation determines situated Agency and authority; Workcell supplies material execution and lifecycle.

The O:I parent presents and connects these native relations through its desktop and other projections. QL-MEF supplies optional formal orientation and refraction. A product relation can be important without being a mandatory runtime dependency. Ordinary Factory operation must not require a QL service merely because a formal reading is available.

This ownership matters during a failure. A stale context binding calls for an attributable return to its owner, not a Factory-owned replacement resolver. A participant becoming unavailable changes the effective execution arrangement, not the authored AgentSet. design-commitment

Return after an absence without reconstructing every chat

On re-entry, the person needs the current Project ground, active frontier and consequential changes since their last encounter. They should be able to follow recognised Candidates, decisive returns and still-open claims. The intended reading explains why the Project is now here before offering lower-level logs.

Durable developmental context makes part of this recovery possible. The native ProjectDevelopmentStore retains an existing Run-scoped ledger and validates its identity on reload. An absent record returns absence. It does not fabricate a development history to fill a presentation. A material relocation can change a binding while preserving the developmental reference.

This account does not claim that every intended re-entry screen is currently installed. It records the UX target and the inspected persistence and identity contracts that support it. Repeated work needs a developmental reason and proof

A Journey may be carried partly through recurring work, but repetition is only useful when it serves the continuing intended difference. Factory retains what the repetition is for, which Run or activity produced evidence, and whether the responsibility is complete or needs to reopen.

vision

Judge the product by meaningful development

The desired result is greater human room for authorship and life away from supervising execution mechanics. A person can entrust a meaningful outcome, inspect consequential alternatives and recognise an actual difference. Agents can recover why the work exists and contribute through stable, inspectable developmental subjects.

The Project should become more intelligible as it changes. Returned failures and unexpected possibilities remain useful findings. Its retained history should explain not only which files changed but what was intended, what evidence challenged the plan and which determination shaped the result.

This closes the relation to [[factory:seed:q5|the Why-For seed]]. The amount of generated code or documentation is not the product’s success measure. The useful test is whether capable development remains connected to purpose and whether returned reality can improve the next act without silently replacing the author’s ground.
